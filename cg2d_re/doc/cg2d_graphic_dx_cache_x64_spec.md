## 2. 首选 A：原生非拥有指针

建议由私有 `DxGraphicEntry` 承载：仅将两个原生非拥有指针拓宽，采用 8 B 自然对齐，不使用 `pack`、不重排，拟定 `sizeof` 为 `0x20`。

| 原字段与偏移 | x64 拟定偏移 | 拟定承载与语义 |
| --- | --- | --- |
| `head` `+00` | `+00` | `TextureNode*`，非拥有 |
| `width` `+04` | `+08` | `std::uint16_t`，保留 W16 位模式 |
| `height` `+06` | `+0A` | `std::uint16_t`，保留 W16 位模式 |
| `palette` `+08` | `+10` | `PaletteCacheItem*`，非拥有 |
| 未知字节 `+0C` | `+18` | 1 B，`uint8` |
| 未知字节 `+0D` | `+19` | 1 B，`uint8` |
| `flag` `+0E` | `+1A` | 1 B，`uint8` |
| 未知字节 `+0F` | `+1B` | 1 B，`uint8` |

新布局的对齐空隙不等于原未知字段。尺寸由消费者按原阶段作 S16 解释或 W16 原位复制，不统一解释为正数；索引步长使用新的 `sizeof`，不改变分阶段读取/写入。

`2,200,000` 项拟占 `70,400,000 B`，即十进制 `70.4 MB`；原表占 `35,200,000 B`，增量为 `35,200,000 B`。该预算不含两池及后端资源。

上述类型、布局与大小均为待批提案，不是已编译验证的大小，也不冻结尚未取证的池成员类型。

### 备选 B：16 B 与 U32 池编码

B 仅作备选：原 16 B 表项加 U32 池编码可节省空间，但需另行闭合来源覆盖、解析、复用及旧引用失效合同；16 B 不代表与原指针字节语义等价。

G1a 尚未闭合 B 的全池域。选 A 不要求继续补 B 的证明；本推荐不新增令牌、代际或注册机制。

## 5. 六阶段合同

### 5.1 初始化

顺序保留为 `BuildSurfaceCache` → 调色板池初始化 → `InitPalette` → `GraphicAlloc` → 引用重置 → `GraphicInit`。

在原时点发布分配结果；四个分配全部成功后才清表。不得提前清零，也不得用事务式发布抹去失败残留。

### 5.2 单图尺寸生产

顺序保留为：原门禁 → 资源 → 取宽低 W16 → 写当前图号 → 写入 `w` → 重读表基址 → 取高低 W16 → 写入 `h` → 建链。

读取失败时清工作输出，不清旧条目尺寸；工作宽度的对齐结果不回写以替代条目宽度。

### 5.3 纹理引用

旧 `image` 解绑、条目 `head` 清除、新 `head` 发布、`next` 链接与 `state` 写入均保留原时点。

扫描使用实际节点数，保留正常位宽、U32 比较、有符号除余与对齐行为。部分链节点不足时不补末节点 `next = 0`，不回滚，不改变外层成功返回。

### 5.4 调色板引用

顺序保留为：旧缓存项的 `image` 失效 → 清条目引用 → 取得缓存项并发布 → 上传载荷 → 复用/老化。

P 状态与 DX 尾字段分开；共享项不逐图释放。绘制时仅清调色板缓存项的 `+0x0C` 状态，不清 DX 条目的未知字节。

### 5.5 重建

顺序保留为 `Destroy` → `Init` → `BuildSurfaceCache` → 节点重置 → 两个引用置 0。

整表不替换、不重新分配，不清 `w/h`、`flag` 或未知字节，不提前使引用失效。

### 5.6 退出

顺序保留为：动态调色板释放且清其池槽 → `node.surface` 释放且清 `surface` → 关闭资源 → 释放 DX 表。

DX 槽与容量不清；失败回收不自动清除。不清槽的残值合同不代表使用悬空引用的问题已解决。

## 14. 已批准：surface 变换缓存键使用 64 位地址

2026-09-27 用户明确“按地址缓存的地方修改为64位”。以下完整原生地址

### 依据与范围

`DrawAllQueued` 的三个上传 caller 已有真实下游 `520B10`；
其后仍分别调用 `44DA90/44D520`，两入口经 `44CD80` 使用两棵

原键首项是 surface 地址的 U32 数值，比较为无符号次序；
后续图号、低 W16 调色板索引和矩形继续按原字段规则比较。
树用于查找、插入与清理；当前直接证据未见按树序提交绘制，
但释放先后依赖该次序，不能声称 x64 下仍有原地址顺序。

本裁决确定 surface 键的 x64 表示和排序差异，不单独决定
`GraphicCacheItem32::dataBits` 的 Yobi 身份，也不改变其他待决 owner。

### 执行方案

1. 缓存键直接保存新端 `TextureSurface*`，以原生指针相等比较身份；
   仅在不同地址的排序比较中转成 `std::uintptr_t`，不截断为 U32。
   不以未关联对象指针的内建 `<` 替代原无符号数值排序。
   绘制/像素读取仍传递同一原生 surface 引用，缓存值仍为实际变换面。
2. 不增加注册表、全局递增 ID、代际或引用计数；不延长 surface 生命周期，
   不借键复制像素快照。相同存活 surface 产生相同首键，其他键分量
   及场景 10/其他场景两树选择按原证据保留。
3. 两树留在既有渲染实现范围内，以标准库有序容器承接；
   不将旧 x86 树节点/28B 栈键当 x64 原始布局，不新增外部依赖。
   实施时继续核完整比较器、构造/插入/命中、副作用和原清理入口，
   未取证字段不凭提案补造。
4. 保留原清理时点及树内逐项释放，不新增按帧清空、隐式失效、
   地址复用保护、失败回滚或假成功。尚未闭合的初始化/销毁父调用

这是 SDL/CPU surface 替换下的表示选择，不宣称原分配地址、
旧 STL 树形或分配失败时机等价；可见像素、查找键其他分量、

不推荐新增稳定 U32 句柄：会增加登记、回收及地址复用语义，
