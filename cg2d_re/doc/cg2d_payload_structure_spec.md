# Yobi payload 结构分析 SPEC

2026-10-10，BPST01。响应用户“这个payload应该是struct你试着分析一下”，范围为当前战斗链的 `YobiAction::payload`。§1–5保留当时仅分析、源码未改的结果；2026-10-11四段字节承载的当前实施见§6–7。旧结构证据JSON保留当时状态，不代本次源码交付。

## 1. 结论与类型来源

战斗载荷可以且已经按结构体表达，当前源码为 `BattleActorPayload`。通用 `YobiAction::payload` 保存不同对象族的独立载荷地址；其类型擦除边界与战斗字段结构是两个层次。

当前IDA命名类型实际声明：

- `YobiAction` 大小330h，原+0Ch成员 `pYobi` 为 `YobiData*`。
- `YobiData` 是union，六个成员偏移均为0；包含战斗角色、战斗场景、重生、地图角色、窗口及文本视图。
- 战斗成员类型 `YobiBattleEntryData` 是struct，声明大小13E8h（5096B）。
- 效果记录 `BattleEntryEffect` 是struct，大小10h，四成员各32位，偏移0/4/8/Ch。

这些是**当前数据库已有声明，原始声明来源未知**，不是获得原C++源码，也不单凭命名类型证明全部字段语义。指令能够独立证明战斗载荷范围、若干字段宽度及队列访问方式。

效果值记录当前已有如下语义，保持16B，不含对象地址：

```cpp
struct BattleEntryEffectRecord {
    std::int32_t position;
    std::uint32_t flags;
    std::int32_t position3;
    std::int32_t position4;
};
```

flags使用U32表达位模式；数据库的int声明不证明原源语言签名。传值仍须保各创建者的四字段读取顺序；这是结构化后仍需遵守的行为合同。

## 6. BPST01-A：四段用途未定字节的存储裁决（2026-10-11）

按用户“先补缺失”及子AGENTS第8条工程委托，先记录本方案后实施：BattleActorPayload在原FFC、104C、1081、13D4四个来源位置分别增加4/4/3/4B的std::byte数组，名称只标原位置，不命名业务、不声明数值或地址类型。这15B的存在及整块清零/复制范围由原13E8H分配和41EAFF整块复制证明；不靠数据库的int/char声明猜语义，也不由未找到字段访问认定它们只是padding。

数组置于相应已知成员之间；字段后缀继续仅为原端来源标识，不用于计算新端地址。当前所有同族创建及浅克隆已使用sizeof(BattleActorPayload)，通用分配器清零整个请求范围，浅克隆memcpy整个原生结构，本步沿这条真实链保留新增字节，不另加清零、默认赋值、字段复制或owner。原生指针、数值字段、两条200项队列及所有业务读取/发布序保持；不pack、不对外暴露固定偏移、不扩大通用void*槽的类型假设。

实施取舍：先消除“原有字节区在新结构中没有承载”的缺口，用途、写者、别名和是否包含需拓宽的地址仍未知；未来取得真实地址证据再单独迁移，当前字节保留不宣称完整x64语义等价。四段不是新增业务数据，也不是原13E8H与新sizeof相等的承诺。已知T*的浅复制/非拥有寿命不改变，完整载荷生产及生命周期仍按原门禁验收。

本轮只读定位[404000,424000)、[424000,440000)两段共66548条已识别指令，未找到位移落在上述四段内的直接内存操作。这仅为后续字段取证线索：算术形成的指针、跨域代码、宽操作覆盖、批量访问及未识别代码不在该筛选闭包，不能据此判未使用。未复制指令/源码JSON或修改IDA类型。
