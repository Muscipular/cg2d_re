# cg2d 完整还原独立执行计划

> 建立日期：2026-09-14。
> 当前状态：文档阶段维护；原端基线冻结、盘点、逆向、重建及运行验证均尚未执行。
> 已确认：原客户端为 x86；原指针按 32 位核对。
> 渲染状态：先前提出 DX11，现已确认以 SDL3 `SDL_Renderer` 替换原 DX7，仅复刻 32 位色渲染；具体平台驱动策略仍待确认。
> 本轮 RPLAN.2 确认渲染接口与色深范围，仅维护本计划及[独立进度](cg2d_full_reconstruction_progress.md)。不修改旧计划、旧进度、生产代码或构建配置，不开始逆向、实现、构建、调试或依赖下载。

## 1. 主线定位与范围

1. 自 2026-09-14 起，以本计划建立完整复刻 cg2d 的独立执行主线。
2. 文档任务使用 `RPLAN.N`；执行阶段使用 `R0` 至 `R8`，细项使用 `R阶段.任务.小步`。
3. 新编号与旧 `M` 系列及 `M6R` 子系列隔离，不沿用其完成状态或验收分母。
4. [旧计划](cg_engine_dev_plan.md) 与 [历史进度](progess.md) 仅供参考，不构成本线已完成证据。
5. 历史源码、测试、地址笔记和用户裁决必须重新核对适用基线，不能自动计入完成度。
6. 目标是在用户确认范围内逐项还原原二进制可证实的函数、数据和内部执行逻辑；渲染采用 SDL3 `SDL_Renderer`，仅其必要替换差异逐项记录。仅复刻 32 位色渲染，8/16/24 位色渲染路径为用户明确排除；原 8 位索引资源读取、调色板读取及转 32 位色解码仍须保留。
7. 本文不声称已确定原文件版本、哈希、函数数量、原地址、结构布局或模块存在情况。
8. 阶段名称只是待盘点范围，不表示原端采用同名模块、类、目录或现代架构。
9. 未知项保持未知；事实冲突或实施方案不确定时停止受影响任务，请用户裁决。

## 2. 内部还原标准

### 2.1 函数身份与调用契约

- 以原二进制可证实的函数边界和代码片段归属建立稳定映射，记录入口、出口及共享尾部。
- 逐项核对签名、调用约定、参数来源与宽度、返回值、寄存器及栈使用、副作用和调用链。
- 原端为 x86 不等于所有函数采用同一调用约定；必须结合调用者、被调用者和指令确认。
- 原源码名称、被内联前的源函数划分通常不能仅凭二进制证明，不能用反编译猜测补全。
- 分析别名与原名称严格区分；边界或签名未确认的条目不得标为完整还原。
- 不以功能相近的新函数拆分、现代状态机或统一调度器替代原有函数划分与调用关系。
- 渲染替换仍须保留原渲染上层函数身份、接口语义、副作用及逻辑时序的可追溯对应。

### 2.2 结构、数组与全局数据

- 逐字段记录偏移、宽度、符号性、对齐、联合覆盖、嵌套关系和实际读写用途。
- 原指针按 32 位核对；不能由 x86 自动推定结构对齐、打包方式或目标工程布局。
- 数组须记录容量、步长、有效元素判定、边界访问和关联计数，不能仅保留有效业务字段。
- 全局数据须记录原始字节、零初始化范围、运行初值、初始化顺序及重置、释放时点。
- 跟踪所有权、别名、共享读写和生命周期，不以现代容器或自动管理对象替换后直接宣称一致。
- 字段名称可用中性别名；未经证实的业务含义、缺失字段和未知填充必须单列。

### 2.3 执行逻辑与可观察行为

- 逐项还原分支条件、循环边界、退出路径、状态取值与转换前后读写，不只覆盖正常路径。
- 核对整数截断、符号扩展、溢出、移位、比较及运算顺序，保留机器可观察语义。
- 记录调用次序、字段更新时点、回调注册与触发、重入、时钟读取和随机数消费次序。
- 网络输入、资源读取及失败返回造成的副作用必须追踪；不能由现有测试预期反推旧端行为。
- 功能可用、截图相似或流程可操作不能替代内部一致性；获批替换差异必须明示。
- EXE 字节相同、固定装载地址、外部 Hook ABI、编译器及优化一致是否纳入，仍待裁决。
- 不擅自扩大或缩小上述要求；若与渲染替换发生冲突，列明冲突并请求确认适用范围。

## 3. 基线与证据规则

1. 先冻结原 EXE、匹配 IDB、资源及运行环境；记录实际路径、版本来源和文件哈希。
2. 核对 EXE 与 IDB 的输入文件、段、映像基址及关键原始字节，不能只凭文件名确认匹配。
3. 确认有无磁盘补丁、加载器、注入组件、Hook 或运行期修改；存在差异时分别登记。
4. 原文件和原数据库保持不变；未经用户授权，不修补二进制，不改 IDA 名称、类型或注释。
5. 同一冻结基线的二进制字节和反汇编是内部语义证据，反编译只用于辅助阅读。
6. 关键结论交叉核对调用者、被调用者、数据读写引用，以及函数表、跳转表的实际表项。
7. 跳转表必须确认输入来源、表项宽度、实际目标和目标指令，不能只信反编译分支标签。
8. 运行观测用于验证路径和时序，不能替代函数边界、字段偏移或未触发分支的静态证明。
9. `server`、`xlsx`、旧计划和现有源码只提供线索，不覆盖原客户端事实。
10. 证据矛盾时保留各自基线、地址及上下文，停止受影响项并提交用户裁决。
11. 禁止先改二进制或 IDA 标注使其符合预期，也不能静默套用历史例外消除冲突。
12. 基线发生变化时建立新标识，标出受影响条目并重新验证，不将不同版本证据拼成结论。

4. DX7 范围之外的原底层 API 与现有 SDL 封装如何对应；未获授权不得顺带更换声音或输入。
5. 原端实际文本编码及字节数组、字节索引与现行内部 UTF-8 规则如何协调；GBK/Big5 等具体编码需按基线核实，不能先转换再丢失布局事实。
6. 部署兼容、外部 Hook ABI、固定装载地址、EXE 字节一致、编译器及优化一致是否属于验收范围。
7. 若发现不能直接用标准 C++ 表达的原端行为，先列机器可观察结果、触发条件及依赖环境；不直接写成 C++ 未定义行为。
8. 对此类行为的确定性表达、隔离方式或修复须先裁决，不能擅自修复或隐去影响。
9. 具体平台驱动策略确认后核实现有 SDK、工具链及适配条件，不直接引入外部依赖或下载组件。

尚未裁决的冲突阻断相关实现；具体平台驱动策略仍待确认，不擅改 `AGENTS.md`、编码、后端或架构。

## 5. 原 DX7 渲染替换边界

- 原 DX7 渲染相关函数和资源先按证据盘点，不预设具体 API、图形效果或资源类别一定存在。
- 为范围内每个原上层函数建立到新实现的映射，保留输入输出、副作用、资源关系和逻辑执行时点。
- 具体平台驱动策略确认后，原生资源类型、API 调用及生命周期确需改变时，逐项记录必要性、替换位置和验证办法。
- 不声称原 DX7 与替换实现的原生对象布局相同，或底层 API 调用能够逐指令一致。
- 除用户明确排除的低色深渲染路径外，API 替换不能扩展为更改游戏逻辑、原渲染排序、坐标、提交次序、调色、透明或画面语义。
- 上述语义的具体形式仍须取证；不能因为计划列出检查维度，就认定原端具有某项效果。
- 逻辑提交次序与新 API 实际调用序列分别记录，必要差异须说明如何保持原可观察语义。
- 资源创建、更新、使用及销毁的对应须覆盖失败路径；只验证画面出现不足以证明生命周期正确。
- 无法直接对应的行为进入差异台账，请用户裁决；同意替换 DX7 不代表任何差异都已获批。
- 替换接口已确认为 SDL3 `SDL_Renderer`；具体平台驱动策略未定，不擅自改用原生 DX11 直连或 `SDL_GPU`。
- 8/16/24 位色渲染路径的原函数、分支仍须盘点并标记“用户范围排除”，不编码、不列为未完债务。资源格式位深不等于渲染输出色深：须保留 8 位索引图的索引、调色板读取及转 32 位色所需调色、解码，不将排除扩大到其他资源处理、字节码或 8/16/24 位整数、协议及结构字段。
- 同一函数包含多种色深分支时，只排除已确认的低色深渲染分支，保留 32 位色及资源解码所需共享逻辑，不能将整个函数标为排除。

### 6.2 R1 至 R3 的拆分原则

- R1 登记可执行代码、数据区域、导入、导出及回调入口；间接调用和未归属片段保留待解析状态。
- 编译器生成函数、运行库、第三方函数与业务函数分开分类，不能因工具标签直接排除。
- R2 从实际入口引用追踪初始化、循环驱动及退出，保留调用次序、状态读写和失败清理。
- R3 按调用链识别平台和资源行为，核对原始资源字节、索引关系、加载与释放，不预设文件格式。
- 每阶段依据真实清单生成细项，不提前虚列成百业务功能或假定存在某个子系统。

### 6.4 R5 至 R8 的拆分原则

- R5 由原收发入口、实际分发表和调用者确定协议范围，追踪解码、处理、状态更新及发送副作用。
- R6 沿真实世界、界面和战斗相关引用逐步展开；名称只标识盘点范围，不引入现代状态机替代。
- R7 检查未归属代码、间接调用、未触发路径、常量表和共享数据，不能仅收尾已知功能。
- R8 汇总逐项静态与运行结果，复查全量清单及例外，不以局部可操作流程代表整体完成。

3. 原始证据：字节或指令片段、来源地址、调用者与被调用者、读写引用及实际表项。
4. 依赖关系：前置函数、结构、全局数据、导入及回调，明确共享读写集合与更新时点。
5. 新端映射：实现路径、符号、对应范围；渲染替换另列原生类型、API 和生命周期差异。
6. 验证记录：静态核对、运行输入与初值、观测结果、验证者及关联变更；未运行明确注明。
7. 未决与例外：问题、影响范围、所需证据、用户裁决及批准日期，保留不同基线的适用限制。

状态区分未盘点、待分析、待裁决、待实现、待验证、已验证、批准例外和用户范围排除；未知不能等同不适用。
编译器、运行库及第三方条目如需排除或由外部实现替代，必须提供分类证据并获用户批准。
不能声称全 EXE 覆盖却自动跳过这些条目；报告分别计数盘点总范围、范围内全量一致性及已验证项、替换例外、用户明确排除的低色深渲染项和剩余未知。排除项保留证据，不计入范围内完成分母或未完债务，不悄悄移出清单。

- SDL-TUI、单当前 `SubScene`、16000 性能目标、GPU 优化和跨平台不自动保留为本线目标。
- 保持现行项目规则及最小修改原则；未确认前不改 `AGENTS.md`、后端边界、编码或整体架构。

## 9. 小步执行流程

1. 主线程从已通过门禁的清单中选一个函数、一个结构或一个有证据的最小调用链。
2. 写明单项编号、基线、输入输出、依赖、共享读写、允许修改路径和验收条件。
3. 使用独立 `xhigh` 子代理分析，交付静态证据、确定结论及未决项；完成后及时关闭。
4. 分析存在不确定或跨模块冲突时先裁决；不允许编码代理依据推测补齐业务逻辑。
5. 由独立 `xhigh` 子代理按批准范围编写最小改动；不顺带重构关联方，完成后及时关闭。
6. 另由独立 `xhigh` 子代理验证原端证据与实现，不由分析或编码代理自验代替；完成后及时关闭。
7. 共享结构和全局写入的任务串行处理，先确认布局契约，再允许无共享冲突的小步并行。
8. 仅按验证需要构建或运行，不默认全量构建、调试或下载依赖；不能运行时记录未验证范围。
9. 主线程仅同步独立进度 `plans/cg2d_full_reconstruction_progress.md`，记录本线编号、证据、改动、验证、例外和遗留。
10. 每个可验证小步通过后按项目规则提交，只包含本步授权路径，不夹带用户既有变更。

用户已明确新线独立管理，覆盖新线沿用旧进度的约定；`plans/progess.md` 仅作历史参考，不写入、不作为新线进度入口。
RPLAN.1 建立计划与独立进度；本轮 RPLAN.2 仅同步渲染接口与色深范围确认，独立验证完成后按上述流程提交；不推进 R0 或生产实现。

|---|---|
| 函数 | 原边界、签名、参数、返回、副作用和调用链均映射；未知内联前划分不冒充已还原 |

### 10.2 原新对照方法

1. 原新采用同输入、同资源和同初值；测试记录绑定原基线、实现版本及环境。
