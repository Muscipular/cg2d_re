# 登录界面约 30 FPS 的采样结果

采集日期：2026-10-13。用户确认 Debug、Release 均约 30 FPS，同机原版可到 60 FPS；基线由用户提供的批处理取启动参数，使用同一游戏目录，采集既有 `/O2 /Ob2 /DNDEBUG` Release 程序。用户确认基线采样窗口仍约 30 FPS。基线未改客户端源码、编译客户端、登录服务器或改动系统计时器／驱动设置；后续按用户要求实施的 1ms 对照另列于文末。

## 结论

基线直接证据将主要等待定位到 `Flip_44C560 → SdlPresenter::Present → SDL_RenderPresent → RTSS 的 DXGI 钩子 → DXGI → D3D11 → WaitForSingleObject`。CPU 逐像素绘制是运行阶段的热点，但不是这次约 33 毫秒帧周期的主要占用。不能再将 Debug 当作本次根因。

后续同一 Release 的软件后端登录界面对照达到约 60 FPS，而自动选择的 D3D11 仍约 30；恢复自动后端后再次复现约 30。当前已将限制缩小到本机 D3D11 提交链，未唯一确定 SDL／DXGI／驱动中的具体同步策略；详见文末对照。

| 统计 | 结果 |
| --- | --- |
| 周期调用栈时段 | 12.009 秒，767 个主线程样本 |
| `SdlPresenter::Present` 在栈中 | 682 / 767，88.9% |
| D3D11 链中的对象等待叶 | 668 / 767，87.1% |
| 主线程睡眠叶 `NtDelayExecution` | 5 / 767，0.65% |
| CPU 追踪第 40–60 秒 | 客户端全部线程 2399 个运行样本，主线程 2124 个 |
| 该 CPU 时段的 `DrawAllQueued` 包含样本 | 1583 / 2124，74.5%；这是运行样本占比，不是整帧墙钟占比 |

本次等待图的周期采样平均约 15.7 毫秒；每次短暂停主线程并读取调用栈，总暂停 468.2 毫秒，占采样时段约 3.9%，最大一次约 7.2 毫秒。图的占比属于抽样统计，存在扰动及相位偏差，不能当作逐帧精确耗时。CPU 图来自独立的系统运行采样，未使用该暂停采样器；第 40–60 秒没有初始化调用栈。

## 调用点核验

使用本次 Release 的 MAP 和实际模块基址匹配客户端函数；没有使用另一构建的 PDB。客户端返回地址 RVA `0x132C72` 对应 RVA `0x132C6D` 的调用，其跳板和 IAT 明确解析为 `SDL3.dll!SDL_RenderPresent`。因此等待发生于最终提交，已区别于 `SDL_UpdateTexture`。

系统 D3D11 的返回地址 RVA `0x13F7E` 对应 `WaitForSingleObject` 调用。调用前把等待上限设为 0 或 2000 毫秒；既有等待样本不能走零等待分支。这不是客户端设置的 33 毫秒睡眠，真正唤醒原因、同步对象及 DXGI／驱动中的帧节奏还未确定。RTSS 钩子出现在链中不等于它造成等待；本机 RTSS 全局配置 `Limit=0`，没有据此改动 RTSS。

## 多媒体计时器问题

基线源码没有 `timeBeginPeriod(1)`／`timeEndPeriod(1)`。原版 IDA 的直接导入中也未发现它们，但这不排除旧 DirectDraw／音频／驱动间接申请高精度的可能。

微软文档说明，Windows 10 2004 起高精度请求按调用进程处理；因此在另一个采样程序中调用，不能保证改善客户端自身的等待精度。该 API 改善计时及等待超时精度，不提高 `QueryPerformanceCounter` 的精度。若验证它，应在客户端内配对申请／释放，并保持同一场景、前台状态、驱动及采样方法作一次对照；本轮未实施这个改动。

目前证据足以说明“主要阻塞在最终提交”，尚不足以将底层原因唯一归为缺少多媒体定时器、驱动强制同步、窗口前后台限帧或 SDL/DXGI 队列策略。下一步应沿提交链做单变量对照，避免先优化 CPU 绘制而掩盖真正等待。

## 1ms 对照方案（用户要求）

用户要求“你先加上试试”。在客户端 WinMain 活动期申请 `timeBeginPeriod(1)`，仅成功时于退出配对 `timeEndPeriod(1)`，覆盖所有早退；不改帧阈值、截止更新、跳帧或 SDL 提交方式。复用已有 Winmm 链接和 Release 构建目录，按相同游戏目录／启动参数运行登录界面。比较 FPS 后复采提交等待，结果在此追加，不预先宣称恢复 60 FPS。

## 1ms 对照结果

`ClientEntry.cpp` 已加入上述生命周期请求；已有 Winmm 链接，无新增依赖。现有 MSVC x64 Release 增量构建完成一次源文件编译及客户端链接，退出码 0。新客户端按相同启动参数／游戏工作目录运行，用户确认仍约 30 FPS。

| 周期调用栈统计 | 基线 | 加入 1ms 请求 |
| --- | --- | --- |
| 时段／主线程样本 | 12.009 秒／767 | 12.014 秒／770 |
| `SdlPresenter::Present` 在栈中 | 682／88.9% | 712／92.5% |
| D3D11 对象等待叶 | 668／87.1% | 703／91.3% |
| `NtDelayExecution` 叶 | 5／0.65% | 4／0.52% |
| 客户端全部线程 CPU 时间增量 | 1.625 秒 | 1.531 秒 |

新样本中等待仍经 SDL、RTSS、DXGI、D3D11，系统返回地址仍为 D3D11 RVA `0x13F7E`。新构建的客户端提交返回地址相应移至 RVA `0x132CC2`，使用本次保存的 MAP 解析，没有拿新 MAP 重算旧采样。后续复采仅做周期调用栈，没有重新采 CPU ETL；旧 CPU 图仍只代表基线。

新周期采样暂停合计 479.7 毫秒（约 4.0%），最大一次 7.3 毫秒；抽样方法和扰动边界与基线相同。两次百分比的小幅变化不能证明回归或改进，用户观测的 FPS 没有恢复。这个对照没有支持“补上多媒体计时器请求即可解除 30 FPS”的判断；主要等待仍在最终提交，具体同步对象／后端／驱动节奏原因尚待进一步区分。

## 提交后端对照方案

先用同版 MAP 只读现有 `gFrameCount`：登录稳定时，该字段在每次 `Flip` 返回后的主循环末尾递增，可独立于 RTSS 显示统计已完成帧数；同时核 `gWindowActiveState`。不暂停线程，不写客户端内存。只读 RTSS 配置，核全局及本程序专属项，不改该配置。

随后保持同一 Release 二进制、1ms 请求、启动参数和工作目录，仅在新客户端进程的环境里设 `SDL_RENDER_DRIVER=software` 作提交后端对照；结束后恢复自动选择运行。SDL 支持通过此环境提示控制未指定的 renderer；当前 `CreateRendererPresenter` 传 `nullptr`，因此不需改源码／编译或系统环境。若该后端不能初始化，记录失败并恢复，不补业务或更改窗口合同。该实验用于区分自动选择的 D3D11 提交链与 CPU 绘制／主循环，不代表批准长期改用软件渲染。资料：[SDL 官方 render driver 提示](https://wiki.libsdl.org/SDL3/SDL_HINT_RENDER_DRIVER)。

## 提交后端对照结果

只读 RTSS 的 `Profiles`，仅有全局／配置文件，没有 `cg2d_re_client.exe` 专属项；全局 `Limit=0`、`SyncPeriods=0`、`SyncLimiter=0`，未修改这些设置。1ms 自动后端客户端的原有帧计数在 5.026 秒递增 151，约 30.04 FPS，窗口活动状态全程为 2，确认约 30 不是仅来自 OSD 显示。

软件后端启动后先采到片头阶段，周期栈包含 `InitLoading`；该组约 60 FPS 的结果单独本地保留，**不作为登录场景证据**。用户随后明确“已经跳过了”，重新采集登录界面；以下两份正式周期图均无 `InitializeClient`／`InitLoading` 调用栈。

| 登录界面对照 | 自动后端＋1ms | 软件后端＋1ms | 恢复自动后端 |
| --- | --- | --- | --- |
| 完成帧数／计时 | 151／5.026 秒 | 303／5.053 秒 | 146／5.025 秒 |
| 只读完成帧率 | 30.04 FPS | 59.96 FPS | 29.06 FPS |
| 窗口活动状态 | 全程 2 | 全程 2 | 全程 2 |
| 周期图 Present 包含 | 712／770，92.5% | 23／762，3.0% | 707／769，91.9% |
| `NtDelayExecution` 叶 | 4／770，0.52% | 587／762，77.0% | 5／769，0.65% |
| D3D11 对象等待叶 | 703／770 | 未出现 | 693／769 |

前两列是同一可执行文件，唯一指定变化是进程环境中的 SDL 提交后端。软件后端对应 GDI BitBlt，提交等待显著减少，主线程转为主循环的帧截止睡眠；保留的 CPU 逐像素绘制足以在这个登录场景达到 60 FPS。不要据此把所有游戏／战斗场景的绘制性能也判为通过。

用户中途要求在**客户端代码内**自动跳过片头并关闭测试进程。恢复自动后端前，仅按该要求将 `InitLoading` 初始阶段改为既有跳过阶段 21，重新编译／链接；主循环及提交代码未变。回测无需按键就进入主循环，约 29–30 FPS 和 D3D11 RVA `0x13F7E` 等待再次出现。因回测多了一项启动差异，不称三列完全同版；其稳定登录栈与帧调度保持。当前运行客户端已恢复自动选择，软件提示仅存在于已退出的对照进程，系统／用户环境变量未改。

软件周期采样暂停合计 186.3ms（约 1.6%），最大 5.8ms；自动回测 446.7ms（约 3.7%），最大 7.1ms。帧计数统计是另外的只读观测，不暂停线程，未将周期采样百分比换算为精确逐帧耗时。RTSS 模块在两份周期采样中均存在；不能从钩子出现与否直接认定因果。

当前结论是**D3D11 提交链限制了本机这个场景的帧率，软件后端可以绕开**；具体阻塞来源仍需区分 SDL／DXGI／驱动策略。计时器请求没有解除限制。未将软件后端固化为默认，也未改驱动或 RTSS；后续若更换默认后端，应基于这个实测差异另做选择。

### 已排除的候选及结论边界

DXGI设备队列上限1→2，接口返回成功，仍29.98 FPS，已撤回候选代码；见[队列日志](release_queue2.log)和[帧数](release_queue2_frames.json)。D3D9客户端候选测得约59.95／60.05 FPS，用户曾确认画面正常；官方D3D9提交吞吐6431次/秒。用户随后明确要DX11，D3D9默认候选已撤回，仅保留[官方对照](official_scaffold_d3d9.log)、[帧数](release_d3d9_frames.json)和历史[候选图](release_fixed_main_wall.svg)／[统计](release_fixed_summary.json)／[帧数](release_fixed_frames.json)。历史`release_fixed`文件名只标识当时采样，不表示最终方案，图标题已注明撤回。

[只读NVIDIA配置脚本](ReadNvProfile.py)没有设置／保存／删除调用；[查询结果](nvidia_profile_read.json)中专属应用返回-166、相关基础／全局设置返回-160，表示没有查到对应项，不能等价于驱动设置成功读取为关闭。RTSS全局Limit=0、SyncPeriods=0、SyncLimiter=0，没有本程序专属配置；没有修改系统、驱动或RTSS设置。SDL官方也有[前台30FPS现象报告](https://github.com/libsdl-org/SDL/issues/9216)，但没有确认结论，不能拿它证明本机G-SYNC／驱动是唯一原因。

### 最终实现与取舍

仅修改呈现器创建：入口明确指定`direct3d11`，该driver包装窗口时设置SDL公开的透明缓冲属性。SDL 3.4.8由此选取DX11 DISCARD传统交换链；实际仍以XRGB8888输入、NONE混合、Alpha=255清屏输出不透明画面。SDL继续管理纹理、提交及设备恢复，保持原主循环、CPU绘制、1ms请求和自动跳片头。Release增量编译／链接通过，已直接更新用户游戏目录。

这是**保留DX11的呈现兼容修复**：证据证明默认flip／窗口合成组合在本机前台存在约33ms提交等待，改用传统组合能够绕开；该实验同时改变交换链和窗口合成策略，尚未唯一定位驱动内部开关。代价是该窗口不使用flip／tearing路径，SDL升级后需重验。当前窗口登录FPS与画面／输入经实测和用户确认通过，不外推全屏、战斗或完整渲染验收。实现合同见[呈现SPEC](../../cg2d_sdl_presenter.md#present-driver-fps-fix-20261013)，SDL行为依据其[DX11源码](https://github.com/libsdl-org/SDL/blob/release-3.4.8/src/render/direct3d11/SDL_render_d3d11.c)与[Windows窗口源码](https://github.com/libsdl-org/SDL/blob/release-3.4.8/src/video/windows/SDL_windowswindow.c)。
