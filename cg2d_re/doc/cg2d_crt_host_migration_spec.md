# CRT 宿主承接范围提案

> 状态：待用户确认。2026-10-02。
> 本文件尚未改变总 PLAN、既有验收标准或源码。当前只有已批准的具体替代继续有效。

## 建议裁决

建议：经原调用关系确认为 C/C++ 运行库的底层依赖，采用当前本机 MSVC/UCRT/STL
对应职责，接受下表明确列出的运行库实现差异；不逐指令重建旧 x86 CRT。
已有真实业务逻辑、兼容层及其共享数据继续保留，不能借此删除或回退已经还原的实现。

这会调整“CRT 自身行为必须与旧版完全相同”的验收边界。
[项目规则第6、8条](../AGENTS.md)要求保留正常/失败语义，并明确工程委托不能降低验收标准；
因此这一范围需要用户明确确认，不将自动续行、沉默或原四入口许可视为同意。

## 已有证据支持的差异范围

| 范围 | 原端与宿主的具体差异 | 建议接受的库边界 |
|---|---|---|
| FILE与低层文件 | 静态流20/3、原条件关闭/宿主无条件收尾、缓冲与描述符发布时点、锁、部分错误返回不同 | 使用宿主FILE/描述符生命周期和库内错误处理；不复刻旧私有流表 |
| 格式化 | 原直接支持%n，宿主默认禁用；原精度163/512边界、宽字符串转换失败计数、浮点格式机制不同 | 接受宿主格式/库错误合同；不全局启用旧选项或重建输出引擎以模拟旧版 |
| 单字符/多字节库转换 | 旧共享locale/代码页与宿主locale分离；宿主另有UTF-8、清零、参数校验和续接状态差异 | CRT内部使用宿主转换状态；应用协议/资源字节边界仍按原合同处理 |
| C++标准库私有实现 | 原字符串/流/容器内部布局、分配与共享方式不同 | 使用现有宿主标准库对象；应用实际依赖的指针借用、别名和寿命仍须逐项保留 |
| 编译器支持与异常框架 | 原x86栈步长、寄存器返回、SEH/C++异常支撑与x64不同 | 由本机编译器及运行库提供，保留业务参数位宽和真实指针类型 |
| 浮点启动/格式私有链 | 原trap函数槽、P5探测、FNCLEX及旧格式转换链；新端直接使用宿主服务 | 不复刻旧CPU探测或私有函数槽；已批准PC53业务数值合同继续有效 |
| CRT内存管理私有链 | 内部堆表、分配顺序、错误/异常及释放策略不同 | 标准库内部内存由宿主持有；已还原的应用分配协议和共享owner继续保留 |

具体证据见[文件与格式化](cg2d_stdio_contract.md)、
[单字符转换](cg2d_legacy_multibyte.md)、
[启动与浮点](cg2d_startup_flow.md)及[内存合同](cg2d_crt_memory_contract.md)。
此表包含真正的行为差异，不是“已经证明完全等价”的声明。

## 即使确认，仍须满足的业务边界

1. 仅接纳经入口、调用和数据归属证明确认为CRT的依赖；不按地址范围、函数名
   或IDA库标志批量划入，也不把第三方/业务函数自动算作标准库。
2. 保留调用参数、格式字符串、调用顺序、返回值在业务中的消费方式、
   资源所有权、RNG消耗与非地址数值位宽；不擅加默认值、业务保护或重试。
3. 接受的是宿主库自身错误/终止/编码状态合同，业务分支仍消费真实结果，
   不能固定成功、吞错误，或把被业务直接读取的旧错误槽/状态留成永久默认值。
   这类直接可见旧状态需要明确适配，不能凭本提案省略。
4. 线上封包、资源/存档格式及明确依赖的正常业务结果仍按原合同。
   若已证CRT差异会破坏这些边界，须做局部兼容适配或保留原实现，
   不能引用本提案允许协议变形、丢字、换编码或数值改变。
5. 保留已实现的LegacyTime、LegacyStringCompare、LegacyMultibyte、LegacyMemory
   及其他兼容逻辑；本裁决不授权为了“全部标准化”删除它们。
6. 旧UI六项待批补值、未知数据容量/生产、4626A0入口参数、未决wire及资源缺失
   仍独立待决；音频继续暂停，屏幕键盘/newest/加密既有排除范围不变。
7. 不引入外部依赖；不开编译、测试、客户端运行或哈希校验。
   本次确认不自动解除当前验证限制。

## 确认后的执行方式

- 先把上述裁决同步总SPEC、项目规则与当前进度，区分“宿主承接已批准”
  和“原行为等价”；只在此次范围调整时进行必要对齐。
- 对已取证的CRT分组集中收口，复用已核实的宿主提供者，减少重复的私有算法取证。
  每项仍保留原身份与调用关系，缺失宿主提供者或存在实际业务冲突的项继续实施。
- 优先处理真实接口缺口、数据生产和接线；源码修改按可验证小步提交。
  不再把每个旧内部槽/辅助指令都当作必须在新端定义的链接目标。
- 总PLAN完成仍须满足全部适用门禁；未编译、未链接、未运行的内容保持未验证，
  不能因为CRT替代被批准就宣称客户端整体完成。

## 不确认时

继续现有标准：四个已批准入口及其他既定窄裁决保持；
新发现的CRT差异仍是需要忠实实现/适配或单独裁决的缺口。
本提案保持待决，不更改任何条目的已实现状态。
