# 图形与动画自动定容 SPEC（RAC01）

日期：2026-11-01。状态：待用户确认，尚未修改源码。

## 目标与范围

按用户要求，`MAX_GraphicCount`／Anime容量由启动时实际资源自动确定，不再读取或依赖 `cgmsv.yml` 的 `MAX_GRAPHIC`、`MAX_ANIME`，也不保留250万／30500的默认容量。YAML仍提供既有 `BinLoader` 路径及组顺序；本项不移除路径配置，不增加运行时热加载或动态追加资源。

用户追加要求：加载时自动剔除无有效引用的Graphic／Anime数据。“有效引用”的根集合、有效性条件及剔除对象尚待澄清，本项未批准具体算法，不将未能发现引用直接当作无引用。

本方案确认后，覆盖[BLM01](cg2d_bin_loader_migration_spec.md)的配置容量、图形查询上界及相关容量失败约定；磁盘格式、组基址算法、后组覆盖、坐标来源、解码、渲染和协议保持。

## 当前源码依据

- `ResourcePaths.cpp::BuildResourcePaths` 读取两个配置容量，`GraphicAlloc_4574E0` 据此分配动画主表、图形DX页目录、图形主表及动画缓存。
- `GraphicInfo.cpp::GraphicInit_459960` 按 `base + seqNo` 写图形表，下一组基址仍为本组记录数加1；MapNo直接索引却沿用图形配置容量。当前最终查询上界只按记录数加预留发布，不覆盖稀疏SeqNo的全部可能下标。
- `AnimationRuntime.cpp::AnimeInit_45BB20` 按完整12字节记录加载、去重及后组覆盖，临时配对表与主表共用配置容量，要求唯一动画数严格小于容量。
- `Yobi/animation.cpp` 仍存在 `imageNo > gMaxAnimateCount9A4A4C + 100000` 拦截；动画编号并非记录数，容量收缩后不能继续使用该判断。BLM01已明确取消此绑定。

## 建议实施

1. 保留现有分配先于加载的启动顺序。在 `GraphicAlloc_4574E0` 分配前预扫配置资源对；只将数据文件与Info均可打开的资源对计入，空路径或打不开仍由既有加载阶段提示并跳过。预扫文件只读，离开该阶段全部关闭。
2. 图形主表与DX目录容量取以下较大值：完整记录总数加 `max(10, 配置组数)`；所有实际 `组基址 + SeqNo + 1`。组基址仍按各组完整记录数加1推进，空／缺失组的间隙也保持。加载后的 `gMaxGraphicCount` 发布这个自动容量，不再缩回纯记录数。
3. MapNo索引单独按实际正MapNo的最大值加1分配，空资源至少保留槽0；在既有资源模块声明具名容量，替换当前MapNo消费者对 `gBinLoaderGraphicCapacity` 的依赖。保持原始MapNo建索引及后组覆盖顺序，不将运行时MapNo字段的既有置零规则提前套入索引统计。
4. 动画主表、缓存及临时配对表按可加载AnimeInfo的完整记录总数加1自动分配。这是去重后数量的上界，保留当前严格小于容量的合同及原有清零顺序；不按最大AnimeNo分配，不更改既有262144项编号索引域。取舍是重复编号较多时仍有余量，但不额外引入第二套去重逻辑。
5. 删除YAML两项容量的读取、默认值和正数校验，旧键即使存在也不再生效；移除不再有消费者的配置容量全局。只替换容量来源，不自动修改用户运行目录配置。
6. 撤除Yobi中“动画编号与容量相加”的拦截，保留静态图分流、真实动画索引查询和动作加载失败处理；不改变动画编号域或创造新编号规则。

## 追加：加载时剔除无有效引用的数据

目标为用户要求的Graphic／Anime无有效引用数据自动剔除；需与定容统一设计，不能先按全部资源永久分配再宣称已按保留数据定容。本节尚待明确以下合同：

- 引用根集合：Graphic存在动画帧引用，也存在地图、界面及Lua按编号直接查询；Anime也由业务按编号选择。仅扫描GraphicInfo／AnimeInfo或动画帧，不能证明其余记录在实际业务中不可达。
- 有效性条件：须明确“无有效引用”是无人使用，还是引用记录存在但其目标数据／动作／帧无效；两者需要不同的判定证据，不能相互替代。
- 剔除对象：须明确针对运行时索引记录、缓存／载荷，还是二者；原始资源文件保持只读，不作磁盘删除、重写或压缩。

确认前的约束：不按MapNo为0、动作数为0、暂未进入缓存或本次启动尚未查询等单一条件擅自删除；不新增配置白名单代替完整引用合同。后组覆盖、组基址、全局图号、AnimeNo、磁盘偏移及现有直接索引消费者不得因剔除被静默重排。

若要求回收运行时表中间空洞，须在明确引用根后补充稳定编号到存储的映射及所有消费者改造方案；此前“直接索引空间保持”的方案不能同时保证消除空洞占用。是否采用该改造待用户确认，不擅自以只跳过载荷加载代替表内存剔除。

## 边界与风险

- 自动适应限于本次启动加载的资源集合；不承诺预扫与正式加载期间资源文件被外部替换仍可继续，不增加热更新或重试机制。
- 稀疏SeqNo与高MapNo仍需各自的直接索引空间；本项不引入哈希替代、重排图号或改变原记录宽度。自动定容不保证内存一定减少。
- 空资源保留既有必要预留；分配失败仍结束初始化，不回退固定容量或截断资源。数学溢出、畸形记录及超出既有字段表达范围的资源不扩展专项处理或验收。
- 不顺带修复既有完整owner、重复初始化、动画包含上界等其他问题；自动定容不能视为这些问题已验收。

## 验收与实施顺序

确认后按“预扫及独立容量 → 配置与分配接线 → 加载／查询消费者”单线程实施，每个可验证小步同步唯一进度并精确提交。

仅静态核对容量生产到所有分配／索引／查询的引用、组基址、覆盖顺序、文件关闭、失败出口、UTF-8及Git差异；不构建、不新增或执行测试、不运行客户端／算法、不检查产物、不计算摘要。真实资源加载、画面及退出验收等待用户另行授权，不以静态检查代替。
