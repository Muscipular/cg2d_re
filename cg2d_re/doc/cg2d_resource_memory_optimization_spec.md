# RMO01：DX 表分页与 PCM 缓存优化 SPEC

状态：**2026-10-23用户批准按SPEC实施；BGM及固定音乐独立，不占64项。实施中，运行验收未完成。**

## 1. 目标与证据

减少 cg2d_re 资源主表常驻内存，保持当前资源编号、图形、调色板、动画属性/坐标及释放行为。用户授权性能检测，并重点询问 184 MiB 主表优化空间。

本次只读实测五张主表请求 184.223 MiB，其中 GraphicInfo 76.294 MiB、DxGraphicEntry 95.367 MiB。DX 的 250 万条记录仅 2,816 条非零；GraphicInfo 则有 2,092,559 条非零。详见[报告与计算口径](profiling/20261023_memory/分析结果.md)和[完整快照](profiling/20261023_memory/完整采样.md)。

## 2. 推荐范围：先处理 DX 表

用户已选择 DX 按需分页。建议每页 256 项，保留现有 40 B 字段布局，不同时做字段压缩、图号重编号或动画表收紧。页目录覆盖现有逻辑图号空间，页内记录保持原生指针和自然对齐，不引入新的全局句柄编号。PCM 缓存作为第7节的独立小步推进，不与 DX 的生命周期改动混成一个验证步骤。

逻辑只读访问未分配页得到全零值；首次写入分配清零页。页在本轮资源生命周期内不搬迁、不回收，避免使现有借用引用失效。销毁时逐页释放，再销毁目录。

图号合法性沿用现有访问边界；分页本身不新增业务拒绝规则，不缩小配置允许的图号范围。动画动作属性和 Coordinate 必须独立保存，不能依据纹理节点是否活动决定其存亡。

首轮改动集中在现有 `GraphicDxCacheState.hpp` / `GraphicDxCache.cpp`、`GraphicAlloc.cpp`、`GraphicDxCache.hpp`，并迁移现有直接消费点：`GraphicPendingQueue.cpp`、`GraphicPaletteCache.cpp`、`DrawAllQueued.cpp`、`PngImage.cpp`。动画侧现有读写属性入口继续保留含义，按需调整失败传递。

## 3. 必须同时解决的行为

1. 区分只读查询和可写取得：只读不得隐式分配，零记录不可作为写入目标。
2. 全表 head/palette 失效仅遍历已分配页，继续保留其余字段；按逻辑容量计算原返回值。不能在启动后通过清零操作再次填满目录。
3. 所有 `base + imageNo`、裸表索引及接收表指针的宽高查询成组迁移；在同一图形绘制流程中复用已取得记录引用，控制额外访问开销。
4. 页内引用不跨表销毁；纹理 owner、调色板池及借用关系不改变。图形资源分配失败的初始化清理覆盖已创建目录和页。
5. 按需分配把部分失败从启动移动到首次写入。现有 `SetGraphicAnimeActionFlags` / `SetGraphicCoordinate` 等入口没有完整失败返回合同，**实施前须给出每个可分配入口的失败传播补充设计**，禁止抛未处理异常、静默漏写或覆盖共享零记录。此项尚未决议，本评估不把它伪装成已经完成的设计。

## 4. 收益与替代方案

- 当前非零分布落在 47 页，40 B 记录载荷与目录合计约 0.533 MiB，较 95.367 MiB 相差约 94.834 MiB。数字只描述本次快照模型，实际运行还包含空写页、其他场景新增页及分配开销；页数可能随运行增加。
- 若优先控制实现变动，可选连续表路线：预扫描核实实际最大图号后收紧分配，DX 所有字段重排至自然对齐 32 B；当前两步合计约减 43.872 MiB。它与分页为替代路线，收益不可重复相加。
- GraphicInfo 后续可独立按已核实的最大实际索引分配，本次容量尾部对应约 12.399 MiB。不能在记录地址被首见表/业务引用后直接 realloc；MapNo 索引容量不随之缩小。
- 暂不选逐图 std::unordered_map，避免把字段访问成本和逐节点分配开销引入每帧热点；也不压缩原生指针或改变资源格式。

## 5. 验收要求

- 静态核对全部 DX 生产/消费与初始化/失效/销毁路径，确认无残留连续表地址假设；零页只读、页内地址稳定、失败传播和空值语义均有证据。
- 在用户明确授权构建和运行验证后，使用同一资源集、地图、分辨率进行前后比较；记录私有提交、工作集、DX 页数/载荷、帧耗时及加载峰值。
- 场景覆盖登录/选角、地图往返、动作与 Coordinate、调色板变化、PNG/大地图、悬停框、战斗、渲染重建和退出。新旧实现的画面和业务行为不能因减少内存而降级。
- 对相同重复场景观察页数是否收敛，并区分应保留的动画元数据和纹理缓存；本方案不擅自删除非零历史字段以追求数字。
- 本轮性能检测授权用于现有进程采样，不视为自动恢复构建、测试、新启动客户端等旧禁令。本次实际仅完成只读取证与文档。

## 6. 决策点

用户已选择 DX 按需分页，连续表收紧仅保留为历史备选；PCM缓存64项，普通BGM与固定音乐独立管理。用户回复“go，按SPEC实施”批准开发；不自动恢复构建或运行验证。

### 6.1 DX分配失败补充设计（随本次实施落实）

- 目录创建失败沿GraphicAlloc原返回0及清理链；页用nothrow分配，失败记录图号并返回空，不抛异常。
- LoadGraphic领取页面失败返回0；TakeGraphicDxCache没有成功返回，页领取失败直接返回，由LoadGraphic通过head为空返回失败。LoadGraphicTexture取得既有页失败返回0。
- SetGraphicCoordinate改为bool；CoordInit检查失败并返回0，由AnimeLoadAction已有失败分支释放本次动画槽资源。
- SetGraphicAnimeActionFlags改为bool；ApplyYobiAnimeFrame传递失败，两条既有动画驱动入口返回其已有的资源失败值-1。无效图号仍沿原先忽略写入的行为返回成功，不扩大输入裁决。
- 清空旧head/palette只Find既有页，缺页即已为空；不分配、不修改其他字段。Read返回只读零记录，Find返回实际可写记录或空，Ensure是唯一新增页入口；不提供隐式分配的可写索引运算符。

## 7. PCM：64 项 LRU 的建议合同

### 7.1 范围和计数

- **已确认：** 用户要求引入 PCM LRU，得知现有64个音效通道后将容量改为64项。不得继续沿用40，也不把之前询问的“允许超额”选项视为已获批准。
- **已批准：** 64项限于普通音效的解码后 PCM；普通 BGM、固定音乐继续独立持有当前播放缓冲，Lua 文件音乐仍沿既有后端。它们不占这64项，也不在本轮引入音乐历史缓存或新解码后端。
- 按不同资源路径计数，同一路径的多个音效编号共享一份不可变 PCM；音效编号、音量、音高、循环、冷却及播放游标保持各自状态。只合并已有完全相同的路径，不做跨路径内容摘要去重。
- 64是缓存条目数，不是MiB上限。本次单个音效F32缓冲最大约10.75MiB，实际内存取决于访问集合，不能用总样本的平均体积推算保证值。暂不擅加另一项字节预算。

### 7.2 数据和加载

- 样本槽常驻路径、采样率、帧数、原PCM长度及有效性等元数据；PCM由缓存项拥有。淘汰缓存不能把有效样本标记成不存在，不能改变上层 sampleIndex。
- 首轮保持现有F32双声道播放表示。转换完成后释放原PCM临时缓冲，避免“64项F32缓存之外仍保留全部原PCM”的半成品方案；保留原length供既有读取使用。单声道压缩不是此次LRU的必要条件，另行评估。
- 为保留现有启动时的资源检查及失败时点，可仍逐项加载/校验，但只让最近64个唯一资源留在LRU，其他只留元数据；后续未命中时重新读盘/转换。若改为启动只登记元数据、播放时才首次解码，会改变失败时点，须作为单独决议，不能混入实现。
- 缺失时的读盘/解码发生在调用播放的业务线程；音频回调只读取已取得的缓冲，不做文件I/O、解码、LRU扫描或对象销毁。首次播放/淘汰后重播可能增加耗时，需要实际验证，不能宣称LRU没有性能代价。

### 7.3 引用和淘汰

- 成功取得用于播放的资源时提升为最近使用；空间不足时淘汰最久未使用且无播放引用的项。循环播放期间始终持有引用，不能为了满足64项而中断既有声音。
- 同文件多通道引用同一项，但各通道保留独立游标和声道参数。自然结束、停止、通道重绑及退出都必须处理引用；“仍保留SDL流对象”不等于“PCM必须永久锁定”。主线程与回调同步后才可实际释放，不能仅在主线程无锁读取 playing 并 free。
- 当64个通道各持有不同资源时，新声音复用某个既有通道；先停止/解除该通道旧播放引用，再申请新资源，腾出可回收项。若仍无可淘汰项，必须显式返回失败，不越过64项、不释放仍在使用的PCM。加载转换中的临时缓冲可能带来短时内存峰值，条目上限不等于整个加载过程无临时内存。
- 保留现有同音效重播路径：`PlaySe_52C450` 命中同通道同音效时直接 Rewind，空间音效也有重播分支；两者必须在重播前重新取得可能已淘汰的PCM。不能只在 PrepareChannel 增加缓存查询，否则会漏掉同音效重播。
- 现有 Rewind/Play 的失败返回多处被忽略。引入读盘/解码失败后，须在直接音效和空间音效入口接回已有失败结果与通道失败状态，不能把无声播放当成功，也不能为绕开此问题而把所有绑定流永久钉在缓存中。

### 7.4 本小步验收

静态核对初始化、Prepare/Rewind/Play/Stop/Release、自然结束、循环及销毁的全部引用和错误分支。获得构建/运行验证授权后，覆盖超过64个不同音效的访问序列、同路径多编号、并发播放、连续同音效重播、循环声音、淘汰后重播及资源加载失败；确认缓存不超64项、引用有效、声音语义保持，记录命中/未命中时的帧耗时、PCM字节量和加载峰值。

DX分页与音频LRU分别记录实际收益。LRU取代了先前音频“长期保留全部去重PCM”的容量模型，不能把旧报告的85.352MiB/125.897MiB再叠加到LRU收益上。
