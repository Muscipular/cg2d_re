# 登录界面约 30 FPS 的采样结果

采集日期：2026-10-13。用户确认 Debug、Release 均约 30 FPS，同机原版可到 60 FPS；本次由用户提供的批处理取启动参数，使用同一游戏目录，采集既有 `/O2 /Ob2 /DNDEBUG` Release 程序。用户确认本次采样窗口仍约 30 FPS。未改客户端源码、编译客户端、登录服务器或改动系统计时器／驱动设置。

## 结论

当前直接证据将主要等待定位到 `Flip_44C560 → SdlPresenter::Present → SDL_RenderPresent → RTSS 的 DXGI 钩子 → DXGI → D3D11 → WaitForSingleObject`。CPU 逐像素绘制是运行阶段的热点，但不是这次约 33 毫秒帧周期的主要占用。不能再将 Debug 当作本次根因。

| 统计 | 结果 |
| --- | --- |
| 周期调用栈时段 | 12.009 秒，767 个主线程样本 |
| `SdlPresenter::Present` 在栈中 | 682 / 767，88.9% |
| D3D11 链中的对象等待叶 | 668 / 767，87.1% |
| 主线程睡眠叶 `NtDelayExecution` | 5 / 767，0.65% |
| CPU 追踪第 40–60 秒 | 客户端全部线程 2399 个运行样本，主线程 2124 个 |
| 该 CPU 时段的 `DrawAllQueued` 包含样本 | 1583 / 2124，74.5%；这是运行样本占比，不是整帧墙钟占比 |

本次等待图的周期采样平均约 15.7 毫秒；每次短暂停主线程并读取调用栈，总暂停 468.2 毫秒，占采样时段约 3.9%，最大一次约 7.2 毫秒。图的占比属于抽样统计，存在扰动及相位偏差，不能当作逐帧精确耗时。CPU 图来自独立的系统运行采样，未使用该暂停采样器；第 40–60 秒没有初始化调用栈。

## 调用点核验

使用本次 Release 的 MAP 和实际模块基址匹配客户端函数；没有使用另一构建的 PDB。客户端返回地址 RVA `0x132C72` 对应 RVA `0x132C6D` 的调用，其跳板和 IAT 明确解析为 `SDL3.dll!SDL_RenderPresent`。因此等待发生于最终提交，已区别于 `SDL_UpdateTexture`。

系统 D3D11 的返回地址 RVA `0x13F7E` 对应 `WaitForSingleObject` 调用。调用前把等待上限设为 0 或 2000 毫秒；既有等待样本不能走零等待分支。这不是客户端设置的 33 毫秒睡眠，真正唤醒原因、同步对象及 DXGI／驱动中的帧节奏还未确定。RTSS 钩子出现在链中不等于它造成等待；本机 RTSS 全局配置 `Limit=0`，没有据此改动 RTSS。

## 多媒体计时器问题

当前源码没有 `timeBeginPeriod(1)`／`timeEndPeriod(1)`。原版 IDA 的直接导入中也未发现它们，但这不排除旧 DirectDraw／音频／驱动间接申请高精度的可能。

微软文档说明，Windows 10 2004 起高精度请求按调用进程处理；因此在另一个采样程序中调用，不能保证改善客户端自身的等待精度。该 API 改善计时及等待超时精度，不提高 `QueryPerformanceCounter` 的精度。若验证它，应在客户端内配对申请／释放，并保持同一场景、前台状态、驱动及采样方法作一次对照；本轮未实施这个改动。

目前证据足以说明“主要阻塞在最终提交”，尚不足以将底层原因唯一归为缺少多媒体定时器、驱动强制同步、窗口前后台限帧或 SDL/DXGI 队列策略。下一步应沿提交链做单变量对照，避免先优化 CPU 绘制而掩盖真正等待。
